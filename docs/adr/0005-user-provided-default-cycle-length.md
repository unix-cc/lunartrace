# ADR 0005：允许用户填写的缺省周期长度作为预测兜底

Status: accepted
Date: 2026-10-10

## Context

ADR-0003 明确拒绝了"无有效样本时回退到默认 28 天"，理由是：那是**应用在编造**一个用户从未说过的数字，
对周期 35 天的人会系统性错误，还给出虚假的确定感。

但由此产生了一个真实的空洞：新用户必须记录满 **3 次经期开始**（2 个有效周期长度）才会看到任何预计。
在那之前，日历上一句"还不能给出预计"。而这个信息其实**只有用户自己知道**：
"我一般 35 天左右、每次 6 天"。同类应用（如参考设计）正是让用户直接填这两个值。

于是问题不是"要不要兜底"，而是"**兜底的值由谁提供**"。

## Decision

1. 在设置里提供两个**用户可选填写**的值：周期长度、经期长度。`null` 表示未填写——**不预置 28 天**，
   因为预置会制造"这个数字是事实"的错觉。
2. 预测依据的优先级：
   - 有效样本 ≥1 → 用样本均值，`PredictionBasis.RECORDS`
   - 否则用户填写且通过范围校验 → 用它，`PredictionBasis.USER_DEFAULT`
   - 都不满足 → 不预测，`PredictionBasis.NONE`
3. **范围校验与有效样本区间完全一致**（周期 `[15, 60]`、经期 `[3, 10]`），越界视为未填写，
   **不做夹取**（夹取等于假装用户填的是别的数）。
   这条是为了避免自相矛盾：应用不能一边拒绝采用实测的 12 天周期，一边允许用户手填 12 天。
4. `USER_DEFAULT` 一律 `confidence = LOW`，因此**不显示排卵日、易孕窗口与阶段**。
   与参考设计不同，但保持一致：用户填的是"周期长度"，不是"排卵日"。
5. 用户填的值**永不进入统计量**：`CycleStats` 的平均值/中位数/趋势只由实测样本产生。
   否则统计页会显示一个用户自己填的数字，却看起来像是测量结果。
6. 预测卡必须显示依据来源（"基于你填写的缺省周期长度 35 天，记录满 3 次经期后会改用你的实际数据"）。

## Consequences

**收益**：把"新用户什么都看不到"的空洞从"必须记录 3 次"缩小到"记录 1 次 + 填两个数"；
不需要任何权限、依赖或 schema 变更（值存 DataStore）；绝大部分用户会在几天内自然过渡到实测数据，
用户填的值自动退居幕后，不留长期维护负担。

**代价（诚实记录）**：

1. **它是"用户说了算"，不是"算出来的"**：用户填 45 天而实际 28 天时，前两次预测会明显偏晚。
   缓解是显式标注来源 + 记录 2 段后自动切换；**不能消除**误填带来的错误。
2. **零记录的新用户仍然没有任何预测**（没有起点可推）。本 ADR 不解决那一档，文案也不得暗示能解决。
3. **排卵信息在兜底状态下是空的**，界面上会显得"比参考设计少一块"。这是刻意的（见 Decision 4），
   但需要 UI 文案解释，否则会被读成功能缺失。
4. **多了一个需要 UI 输入的设置项**，与 `PRODUCT.md` 的"克制"原则有张力：克制不等于什么都不问，
   但每加一个设置项都要能被用户看懂"为什么需要它"。
5. **口径分支增加**：预测现在有三条来源（记录 / 缺省 / 无）。`basis` 字段让 UI 必须显式处理三种情况，
   不能再假定"有日期就一定是算出来的"。

## 准入三门槛自检

- 难回滚？**是** —— 它决定"应用凭什么说这句话"，一旦用户习惯了兜底值，撤掉会让日历重新变空。
- 无上下文会困惑？**是** —— 后来者必然要问"ADR-0003 不是说不给默认值吗，这个为什么可以"，
  答案就是"谁在断言"这一条。
- 真实取舍？**是** —— 备选是"继续什么都不显示"（空洞留存）与"应用自己选一个默认值"（ADR-0003 已拒绝）。
