# ADR 0001：采用按风险分级的单人工程工作流

Status: accepted
Date: 2026-10-10

## Context

本仓库是单人开发的 Android 应用，作者 + AI 助手协作。协作中出现过的真实问题：

1. **小改付大流程成本**：给统计卡加一个指标，却要先写 spec、再审查计划，实际改动 20 行。
2. **约束文档写了没人读**：一旦文档先于习惯存在，就变成装饰。
3. **约束体系自我膨胀**：每遇到一个坑就加一条规则，规则维护成本最终吃掉开发时间。
4. **AI 会话之间丢失上下文**：跨会话接手时，不知道"上次做到哪、为什么这么定"。

样本项目（bk-lite）用"多套工作流并存"的失败教训换来了结论：多套强制入口会重复加载指令、制造额外工具回合。它最终砍掉全部仪式，只保留两条路径。

## Decision

1. 只保留**两条路径**，高成本入口**默认关闭**：
   - 快速路径（默认）：核对事实 → 实现 → 聚焦验证 → commit。不建 spec、不做计划审查。
   - Grill 路径（显式触发）：`grill-plan` → 对抗审查 → 实现。
   触发条件写在 `docs/agents/workflow.md` §3（改预测口径 / 改 schema / 触碰隐私红线路径 / 需求模糊 / 塞不进一个上下文窗口）。
2. **"什么算小改"必须写下来**（单文件 ≤5 个、diff ≤300 行、不改 schema、不碰隐私路径、不加依赖、现有接缝可覆盖），否则分级判定会失控。
3. 文档分五层，各答一个问题，**禁止互相复制**：`CONTEXT.md`（术语）/ `specs/capabilities/`（长期契约）/ `specs/changes/`（这次改什么）/ `docs/adr/`（为什么）/ `docs/agents/` + `DEVELOP.md`（怎么做）。
4. 约束分级绑定机制：**L1** 本地 git hook（强、绕不过）/ **L2** CI（中、留痕）/ **L3** 文档自评（弱、靠人）。标 L3 的必须显式写明"未自动化"。
5. **不引入第二套工作流**（见 `docs/agents/skills.md` §3）。
6. 评审机制适配单人现实：CODEOWNERS 仍然启用，但不是找人评审，而是把敏感路径钉成**强制自审清单**；自审记录必须双轴分列（Standards / Spec）并标注"同源自审，独立评审不可得"。
7. **拒绝预防性过度设计**写入 `CLAUDE.md` §4，作为约束体系自身膨胀的刹车。

## Consequences

**收益**：小改的成本回到小改本身；跨会话靠 spec 与 ADR 恢复上下文；红线有 L1 强制力，不靠自觉。

**代价（诚实记录）**：

1. **需要靠人判断风险等级**。判断错了两头都亏：走快速路径改了口径（历史数据解读被静默改变），或小事走了 Grill（浪费时间）。缓解是 `workflow.md` §3 的硬条件，但边界仍需判断。
2. **文档漂移是长期风险**。capability 描述的口径可能落后于代码。已知唯一可靠的缓解是"改行为即改文档"的纪律与 review 的 Spec 轴，**没有自动门禁**，本 ADR 不假装有。
3. **没有独立评审**。双轴自审是同源的，系统性盲区（尤其是自己没想到的边界情况）不会被自己发现。这是本仓库最大的结构性缺陷，只能记录，不能消除。
4. **L1 门禁会拖慢提交**：detekt + 单元测试在每次提交时跑，Kotlin 文件多时会有秒级~十秒级延迟。已用"仅 Kotlin 文件变更时触发 + Gradle 增量"缓解。
5. **单人项目缺 CI 之外的兜底**：无第二人复核，机器写错的时候没有人会拦。

## 准入三门槛自检

- 难回滚？**是** —— 工作流决定后面所有文档怎么写，改主意的成本是重写整个仓库的文档结构。
- 无上下文会困惑？**是** —— 后来者（包括半年后的自己）会问"为什么小改不用写 spec、什么算小改"。
- 真实取舍？**是** —— 备选方案是"全部改动用重流程"（bk-lite 证明会失败）与"完全不设流程"（质量靠运气）。选了中间。
