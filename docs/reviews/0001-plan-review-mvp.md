# 计划对抗审查：MVP（离线经期与症状记录）

独立性：**同源自审（不可得独立评审）**
轮次上限：5（本轮为 Round 1）

---

## Round 1

### 严重

1. **"顺手加个默认 28 天回退"会在无数据时给出虚假预测。**
   证据：初版口径写"无有效样本时取 28"。这会直接复刻 ADR-0003 明确拒绝的"固定 28 天"失败模式：
   一个周期 35 天的用户在没有任何有效样本时会被给出错误的预计日期。
   影响：数据正确性（误导用户）。
   → 采纳：改为"有效样本 0 → 不预测（`NONE`）"，并同步修改 `CONTEXT.md` 与 `specs/capabilities/cycle-prediction.md`。

2. **顺推没有上限会指向荒谬的远期日期。**
   证据：初版只有"若起点已过期则加一个周期"。若用户两年没打开应用，循环仍会算出"下次经期"。
   影响：数据正确性 + 用户信任。
   → 采纳：加 `MAX_FORWARD_STEPS = 24`，超限则不预测（但保留置信度，因为样本本身是有效的）。

3. **数据删除写成"清除"但实现容易退化成标记删除。**
   证据：`CLAUDE.md` 承诺"真删除"，而 Room 里最省事的做法是加 `deleted` 列。
   影响：对用户的承诺变成谎言（数据仍在设备上）。
   → 采纳：`wipeAll()` 直接 `DELETE FROM`，并加入 `scripts/check-privacy-guards.py` 的禁止项
   （禁止 `fallbackToDestructiveMigration` 与 `SharedPreferences`）。

### 高

4. **"全仓覆盖率 ≥75% 硬门禁"在单人项目里会阻塞所有小改。**
   证据：指南的按风险分级明确要求"不为小改付大流程成本"；单人没有 CI 资源与第二人来兜底。
   → 采纳：只对 `domain/prediction` 与 `data/security` 设 85% 门禁，其余标注未落地。

5. **DAO 测试会变成"写了不跑的测试"。**
   证据：本机无设备/模拟器，instrumented 测试无法进 CI；而 bk-lite 的坑 4 正是"2095 个测试没有一个在 CI 里跑"。
   → 采纳：明确不做 DAO 自动化测试，并把该决定写进 spec 的 Testing Decisions。

### 中

6. **"未来日期标记"未定义，会让周期长度出现 0 或负数。**
   → 采纳：允许标记未来，但统计与预测只使用 `date ≤ 今天`。

7. **`confidence` 与"无预测"的关系存在二义。**
   证据：两种情形都会出现"日期字段为空"——样本不足，与顺推超限。
   → 采纳：只保证单向不变量（`NONE ⇒ 日期字段为空`）；顺推超限时保留真实置信度，
   UI 文案用"暂时没有可用的预计"，不宣称"记录不足"。

8. **CODEOWNERS 在单人项目里容易退化成注释（bk-lite 的坑 3）。**
   → 采纳：CODEOWNERS 启用，并让 `scripts/check-docs.py` 校验"生效规则 ≥3 条"，
   把"空转"变成可判定的失败。

9. **隐私守卫如果只写在文档里就是装饰。**
   → 采纳：`scripts/check-privacy-guards.py` 作为 L1 强制项，检查清单权限、`allowBackup`、
   日志 API、`SharedPreferences`、`FLAG_SECURE`、PIN 派生算法。

### 低

10. **计划未说明代码落点，存在误写入已有项目目录的风险。**
    证据：`C:\code\frontend` 下已有 10 个无关项目。
    → 采纳：独立子目录 `C:\code\frontend\lunartrace`。

11. **计划里写了两个 CI workflow，但两者检查项完全重叠。**
    → 采纳：合并为一个 `android.yml`（含文档一致性步骤），避免同一约束出现在两处。

VERDICT: **REVISE**（以上 11 条中 11 条采纳，已全部落回计划与仓库文件）
