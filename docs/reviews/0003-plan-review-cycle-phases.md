# 计划对抗审查：周期阶段与排卵期呈现

独立性：**同源自审（不可得独立评审）**
轮次上限：5（本轮为 Round 1）
审查对象：`specs/changes/cycle-phases/spec.md`

---

## Round 1

### 高

1. **"排卵期"与"易孕窗口"会打架。**
   证据：既有口径里易孕窗口是 7 天（排卵日 −5 .. +1，来自精子存活时间的群体假设，见 `cycle-prediction.md` §2）；
   本轮若再展示一个 3 天的"排卵期"区间，界面上会同时出现两个天数不同、含义不同、都声称在"中间"的区间，
   用户无法判断该信哪个。
   → 采纳：**只展示"排卵日预计"这个单日**，不把排卵期作为区间展示；
   `OVULATION` 阶段（排卵日 ±1）只用于内部分类与阶段标签。spec 口径表与 UI 决策已按此修订。

2. **日历新增第四种标记无法在本轮验证。**
   证据：本轮没有真机/模拟器（`docs/reviews/0002` 已记录：UI 无自动化），而日历格子已有
   "实测经期 / 预计经期 / 易孕窗口 / 症状点"四种视觉元素，再加一种必然涉及对比度与拥挤度判断。
   在无法看屏幕的情况下改视觉，等于把"看起来对不对"交给运气。
   → 采纳：**本轮日历视觉不变**，排卵信息通过预测卡文字呈现；配色/标记改动留到能在真机核对时再做，
   并把这个取舍写进 spec 的"明确不做"。

3. **新用户会以为功能坏了。**
   证据：阶段与排卵日依赖排卵日，而排卵日仅在 `confidence ≥ MEDIUM`（≥2 个有效周期长度）时存在；
   一个只记录过 1 次经期的用户，界面上既没有阶段也没有排卵日，也没有任何"还差多少"的提示。
   → 采纳：UI 必须给出进度性说明（"再记录 N 次经期开始就会显示"），并在 spec 的 User Story 4 中固化。

### 中

4. **"周期第 N 天"在长期未记录时会是一个很大的数字，是否违反"不制造焦虑"？**
   证据：`PRODUCT.md` §3 明确反例是"你的经期已经推迟 5 天"——被禁止的是**评价性表述**，不是客观事实。
   → 采纳：允许显示事实；同时在口径里写死"禁止任何评价性文案（已推迟 / 异常 / 是否排卵 / 安全期）"，
   并用测试用例 8 固定"顺推超限时 cycleDay 照实很大、phase 为 UNKNOWN"这一行为。

5. **`cycleDay` 是事实、`phase` 是推算，两者的数据门槛不同，实现时极易一刀切。**
   证据：`cycleDay` 只需要"最后一段经期起始日"（纯事实）；`phase` 依赖排卵日（推算，门槛 ≥MEDIUM）。
   如果实现时统一 gate 在 MEDIUM 上，User Story 1 就落空了。
   → 采纳：spec 口径表把两者分开写，并用测试用例 2 与 7 双向固定该差异。

7. **`UNKNOWN` 混在同一枚举里，容易被 UI 忽略成一个空值。**
   → 采纳：spec 明确要求 UI 在 `UNKNOWN` 时给出文字说明，而不是留白（留白会被读成"坏掉了"）。

### 低

6. **`CycleInsight` 增加字段是否冲击既有测试？**
   核对：`CyclePredictorTest` 与 `CycleMathTest` 只消费 `analyze()` 的返回值，从不构造 `CycleInsight`；
   `ui` 侧只有 `CalendarScreen` / `StatsScreen` 读取字段。
   → 无破坏，无需处理。记录在此以免后人重复核对。

8. **是否需要新 ADR？**
   判定：ADR-0003 决定的是"算法选型与置信度分档"，本轮决定的是"阶段与排卵信息如何呈现"（产品语义），
   属不同决策，且真取舍存在（呈现 3 天区间还是单日、是否新增日历标记）。
   → 采纳：新增 `docs/adr/0004`，并在 0003 标注被其扩展。三条准入门槛逐条自检通过。

VERDICT: **REVISE**（上述 8 条中 6 条落地为 spec 修订；第 6 条判定为无需处理，第 8 条产出 ADR-0004）
