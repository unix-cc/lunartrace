# 工作流：按风险分级，高成本入口默认关闭

> 本文只回答"这次改动该走哪条路径"。**不写代码规范**（那在 `specs/capabilities/`），**不写 spec 模板**（那在 `docs/agents/issue-tracker.md`）。

## 1. 两条路径

```
快速路径（默认）：目标清晰的小改
  核对当前事实 → 实现 → 聚焦验证 → commit
  不建 spec、不做计划审查

Grill 路径（显式触发）：模糊 / 跨域 / 破坏性 / 难回滚
  grill-plan（写 spec 草案 + 对抗审查）→ 单会话直接实现
                                        → 跨会话先 to-spec 再实现
```

**关键：高成本入口默认关闭。** 日常对话不自动进入 Grill 路径，只有下表中任一条件成立才显式开启。

## 2. 什么算小改（快速路径的准入）

同时满足以下全部：

- 单个改动能在一个上下文窗口内完成（约 ≤ 5 个文件、≤ 300 行 diff）
- 不改数据库 schema、不改 `specs/capabilities/` 里的契约不变量
- 不触碰隐私红线路径（`AndroidManifest.xml`、`data/security/`、`data/prefs/`）
- 不需要新的依赖
- 现有测试接缝能覆盖（否则说明接缝选错了）

**例子**：修日历格子边框在跨月时的错位、给统计卡加一个"中位周期长度"、把置信度文案改成 `PRODUCT.md` 口径。

## 3. 什么必须走 Grill 路径

任一成立即触发：

| 触发条件 | 为什么 |
|---|---|
| 改动会改变预测口径（基准长度、置信度分档、易孕窗口） | 难回滚：用户历史数据的解读会变 |
| 改 Room schema / 迁移 | 难回滚：已有用户数据可能损坏 |
| 触碰隐私红线路径 | 事故成本最高 |
| 出现"我还不确定要什么" | 模糊需求，先收敛 |
| 一个 ticket 塞不进一个上下文窗口 | 需要拆片 |

Grill 路径动作：
1. 落 `specs/changes/<slug>/spec.md`，状态 `draft`
2. 做一轮**对抗审查**：逐条给证据 + `VERDICT: REVISE|APPROVED`，轮次封顶 5 轮，记录进 `docs/reviews/`
3. 审查通过 → 状态 `ready` → 实现
4. 完成后状态改 `done`，**原地更新，不 archive**

## 4. change spec 与 ticket 的分界

- 工作塞得进一个上下文窗口 → 只写 `spec.md`，**不建 `tickets/`**
- 超出，或存在真实阻塞边 → 建 `specs/changes/<slug>/tickets/<NN>-<slug>.md`，按垂直切片拆

不创建 proposal / design / plan / delta / tasks 这类 sidecar 文档（多一份文档 = 多一处漂移源）。

## 5. 单人项目的评审替代机制

本仓库没有第二个评审人。CODEOWNERS 仍然启用，但它的作用是**把敏感路径钉成强制自审清单**：

- 改动命中 `.github/CODEOWNERS` 列出的路径时，必须在 `docs/reviews/` 留下一条自审记录（用 `SELF-REVIEW-TEMPLATE.md`）
- 自审记录必须包含：Standards 轴发现、Spec 轴发现，**两轴分列，不合并、不重排**，最后一行汇总"每轴发现数 + 每轴最严重问题"，**不跨轴选赢家**
- 自审记录必须显式标注 `独立性：同源自审（不可得独立评审）`

> 双轴分开的理由：一个改动可能过一条轴、挂另一条轴。
> 规范全对但实现错了东西 → Standards 过、Spec 挂；需求全对但破坏约定 → Spec 过、Standards 挂。

## 6. 收口（完成定义）

```
实现 → 代码就绪但未提交时做双轴自审
     → 处理每条被接受的发现
     → 声称完成前重跑与任务匹配的检查并检查输出
     → 同步更新受影响的 capability + change spec 状态
```

> 来自更早会话或提交的证据是过期的。**旧证据作废，必须重跑。**
